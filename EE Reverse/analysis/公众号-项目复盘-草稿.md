# 17 张图，和一堵墙

**——一个 AI 逆向闭源软件的复盘**

## 01 那天晚上，六张图没了

那天晚上，我把六张画好的图弄丢了。

没有崩溃，也不是数据损坏。我按了 Ctrl+S，看它转完，关掉文档。第二天打开，什么都没了。

原因后来查清楚了：这个编辑器只写"已修改"的文档。我在内存里一张一张画图，对象字段都对，画布上真的出现了图形，但文档的脏标记一直是 0。Ctrl+S 一检查，发现没改，就跳过了。关文档的时候，它也没提示保存。

这件事之后我才明白，这个项目真正的对手不是"怎么画出一个等边三角形"，而是"你怎么知道它真的写进去了"。

## 02 我们想做的事

试卷的源文件是一种私有格式，里面的插图是位图。把位图换成原生矢量图，放大不糊、可以改、能和卷面其他对象一起排版。

人能做，但慢。一套卷子三十多张图，一张一张描，一天就过去了。

于是我搭了一条链子：用 Frida 把编辑器进程挂住，在它内部读写对象；外面套一个 MCP 服务，把这套能力包装成 24 个工具；再让 AI 通过这 24 个工具去画图。

听起来顺。前面也确实顺。

## 03 成绩单

先把数字摆出来，免得后面像在找借口。

| 项目 | 数量 |
|---|---|
| MCP 工具 | 24 个 |
| 桥接 RPC | 91 个（3632 行 JavaScript，跑在编辑器进程里） |
| 服务端代码 | 2320 行 |
| 画成的矢量图 | 17 张（最复杂一张 26 个原生对象、12 处填充） |
| 案例卡 / 几何约束 spec | 6 份 / 24 份 |
| 分析文档 | 170 篇 |

更重要的是"画成了"这三个字的具体含义：关掉文档再打开，图还在；拖一下坐标轴，函数图像跟着动；换个版面，线不糊。

逆向出来的东西包括：原生坐标轴、原生贝塞尔函数图像、原生圆弧、角度与直角标记、加粗点、真正的虚线、调用引擎 API 的灰色填充，以及能正确落在文档字体槽上的字母标注。

这些不是贴图，是引擎自己的对象。这一步是真的做成了。

## 04 第一堵墙：它有状态，而且会报复

我删过一个自己刚建的多边形。

找到删除接口，调用，返回成功。然后整张画布上所有对象都点不动了。颜色微微变了，点哪里都没反应，像一张被拍扁的画。

后来才明白：那个底层删除函数只负责把对象从链表上摘下来，不负责修邻居的指针。摘完之后，前后两个对象还指着它。这个编辑器没有防御。

同一个下午，我还试过另一件事：取消填充。调完，画布上 24 个对象全部消失。

再后来，我手工拼装了一个对象。类型字、样式字、字段布局，和引擎自己造出来的逐位一致。挂上去的瞬间，链又被写坏了。

这三件事合起来是一条规矩：在闭源软件里，"正确"不是"字段对"，而是"这个对象是谁造的、谁拥有它、它挂在谁的链上"。后三件事，你从内存里读不出来，只能从崩溃里学。

## 05 第二堵墙：这里没有单元测试

填充是最典型的例子。

我试过两种配方：给形状的某个字段直接写颜色，或者写一个灰阶。两种做法在内存里读回来，都和"用填充工具画出来的图形"一模一样。但图形就是不填充。

正确做法是调用引擎自己的 `SetSolidBrush`，然后——这是关键——调用 `GetBrush()`，看它返不返回非空。返回 0 就是没填上，字段再对也没用。

字体也是。字体槽是文档级的，每次打开都可能变。记错一个槽号，它不报错，只是把整页字母画糊。

坐标轴更是。不设那个定位矩阵，轴就画在画布左上角；标志位不对，画出来只剩一堆光秃秃的刻度短线。

这里没有 assert，没有返回值告诉你做错了。唯一的判据是人看一眼。

## 06 第三堵墙：它不肯给你的东西

编辑器自己有"输入解析式出图"的功能。我想把它自动化：填公式，点生成。

控件 ID 全读到了，按钮也能点。但那个公式输入框，跨进程怎么写信都返回 0。MFC 只认真的键盘输入。最后这一步只能人来按。

比这更根本的是：它生成出来的函数图像是一个编辑器私有类。我用引擎工厂去造，返回 system error。也就是说，我可以画一条数学上完全一样的曲线，但永远造不出一个"和它一样、能跟坐标轴联动"的对象。

再加上那个脏标记——桥画的东西不标脏，保存就静默跳过。

到这里，天花板的位置就很清楚了：不是"你能不能做到"，而是"对方愿不愿意把状态暴露给你"。

## 07 为什么效率不稳定

这是我最想写清楚的一段，因为它看起来像"AI 不行"，其实不是。

这条链上每一步都依赖外部状态：光标有没有绑在正文里、画布句柄有没有失效、进程还在不在、文档是干净还是脏的。

跑一条 shell 命令就会抢焦点，光标解绑。重开文档，所有句柄作废。删一个对象，整张画布报废。而做错之后没法小步回退——这个编辑器没有事务。

于是 Agent 每一轮都得重新建立上下文，可它看不见这些上下文。结果就是：同一段代码，昨天能跑，今天不能，而它不知道为什么。

不是模型太笨。是它在一个没有单元测试、没有事务、没有稳定 ID 的环境里写代码。

## 08 做对的两件事

第一件：约束式构造，不是像素拟合。

第一次画等边三角形，我是照着原图量像素画的。画完，三边是 21982、21919、21685——差 1.35%，肉眼几乎看不出来，但题目明明写着"等边"。

后来改成：从题干里抽约束，AB=BC=AC、F 是 AC 中点、∠DFE=60°，只保留最少的自由参数，其余全部推导。落笔前用几行代码自检：该相等的边长差小于万分之一，该是 60° 的角误差小于 0.01°。

这个转变跟 AI 没关系，跟"你到底在解什么问题"有关系。像素是观测值，约束是事实。用观测值硬拟合，误差会被放大；用事实推导，误差只剩取整。

第二件：把"验证"当成一等公民。

最后沉淀下来的是一道道闸门：填充完必须 `GetBrush` 非空；挂画布前必须确认构造流程里有 `oncreate`；新画布必须 `frameType` 正确；保存完必须看文件的时间戳和大小，不相信"已保存"这三个字。

每一道闸门都是掉进坑里之后立的。闸门不产出功能，但它是这个项目最贵的资产。

## 09 为什么停

要把它做成产品，还缺几样东西：稳定的对象 ID、可靠的脏标记、可回滚的事务、无头运行的模式。

这四样，恰好都是闭源软件不肯给的。

继续投入的边际收益已经可以算了：画图这一段是能用的，自动化那一段过不去。再花三个月，最好的结果是把"能用"打磨得更顺，最坏的结果是再丢一次六张图。

所以"上限就这样了"是一句工程判断，不是认输。

## 10 给同路人的六条

1. 先问"能不能验证"，再问"能不能实现"。验证不了的东西，实现了也是薛定谔的。
2. 只信句柄和所有权，不信字节。字段全对可能仍然是错的。
3. 一切不可逆操作之前先保存。保存之后验时间戳。
4. 不要和输入注入较劲。如果对方只认真键盘，那就让真人来按。
5. 给"人的注意力"做预算，不只是给 token 做预算。每张图的验收都要一个人看。
6. 学会识别结构性天花板：当你需要的东西恰好是对方没暴露的，别硬凿。

## 结尾

项目停在这里。

编辑器还开着，最后一张画布上有 26 个对象，全部是原生矢量，能拖能改。没画完的先放着。

我们没翻过那堵墙。但墙在哪、有多厚、哪一段能凿，量出来了。

这大概是 AI 现在能替人做的最诚实的一件事：它不保证帮你翻墙，但它能陪你把墙一寸一寸量清楚，然后在你说"到此为止"的时候，递给你一张画好的地图。

那张地图是 170 篇文档、24 个工具、17 张图。

还有一条写在最前面的规矩：不要点删除。
